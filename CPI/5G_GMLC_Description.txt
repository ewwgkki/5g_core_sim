Introduction

The Gateway Mobile Location Center (GMLC) deployed in 5G core (5GC) network
supports control plane positioning for subscribers in the standalone New Radio
(NR) network.

2.1

Technical Description

GMLC Overview

The NLG implements the GMLC Network Function (NF) defined by 3GPP
standards. This section gives an overview of the 3GPP Location Services (LCS)
architecture and the interfaces related to the GMLC.

The 5GC architecture is service-based. The system functionality in Service-Based
Architecture (SBA) is achieved with a set of NFs that provide service access
to other authorized NFs. Authorization can be achieved by enabling OAuth 2.0
support. An NF is a component of the network infrastructure that provides a
specific functional behavior, such as location determination. An NF is made up of
NF services.

The interactions between NFs are represented in the following ways:

— Reference point representation

— Service-based representation

Figure 1 shows the reference point representation of 5G LCS defined by 3GPP
TS 23.501, where the interaction between NFs is described by point-to-point
reference points.

Figure 1    5G LCS Reference Point Representation

The following reference points support LCS in 5GC:

The 5G GMLC enables the external client to request the location of a target UE in
the 5G network. The 5G GMLC uses the Nudm interface provided by the UDM to
request information about the AMF node that is connected to the given UE.

The 5G GMLC also uses the Namf interface provided by the AMF to request
positioning information of a specific UE. The 5G GMLC also interacts with the
NRF through the Nnrf interface for NF service framework functions.

The 5G GMLC can also receive NI-LR notifications on the Namf interface about
positioning results performed at emergency call setup and send the location
information to the LCS client.

The 5G GMLC supports sending user-agent header on the Namf, the Nnrf, and the
Nudm interfaces with a configurable value. For more information, see the Http2
section in Parameter List for NLG.

According to the 3GPP 23.501 standard communication models, there can be
direct or indirect communication performed with external NFs. In the latter case,
the communication is done through the Service Communication Proxy (SCP).
GMLC is prepared to communicate with AMF and UDM indirectly.

GMLC only supports indirect communication model C.

GMLC does not support the following:

— indirect communication model D

— the delegation of NF producer selection to the SCP

2.2.2.1.1

NF Discovery

Figure 4    NF Discovery Procedures

The Service Discovery function is used to retrieve information about the UDM or
the AMF. In every case, the 5G GMLC sends a GET request over HTTP2 towards
one of the configured NRF servers. The syntax of the request is the following:

<Server Address><API Prefix>nnrf-disc/v1/nf-instances?<Parameter List>

The following types of discovery procedures exist:

— Nnrf_NFDiscovery_request(InstanceID)

— Nnrf_NFDiscovery_request(UEID)

— Nnrf_NFDiscovery_request(NodeType)

All the listed discovery procedure paths contain the RequesterNFType parameter,
which is always GMLC, and the TargetNFType parameter, and they vary
depending on the type of the discovery procedure.

When OAuth 2.0 is configured, a valid access token must be provided in the
request header.

For more information on the RequesterNFType and the TargetNFType
parameters, see the Parameter List table in AMF Provide Positioning Info Query
on page 13.

The response to a discovery request is called SearchResult, and it is received
in JSON format. The SearchResult contains a validityPeriod integer and an
array of NFProfiles called NfInstances.

Nnrf_NFDiscovery_request (UEID)

This procedure is similar to Nnrf_NFDiscovery_request (InstanceID). The
difference is that it uses one of the unique IDs given by the LCS client instead of
the InstanceID.

The Target NF Type parameter is set to UDM. The service-names parameter
must be set to nudm-eucm. The User Equipment Identifier (UEID) parameter is
either supi or gpsi, and corresponding to that, either the supi or the gpsi
parameter is set.

The IP addresses and the API prefix obtained as the result of this procedure are

Nnrf_NFDiscovery_request (NodeType)

This discovery procedure is used for the periodical cache refresh.

The Target NF Type parameter must be set to AMF or UDM.

The IP addresses and the API prefix obtained as the result of this procedure are
used in the 5G GMLC. If the target NF type is set to UDM, the UdmInfo field is also
parsed after a successful discovery, and used to build the UDM cache.

The UdmInfo contains supi ranges and gpsi ranges, which determine which user
equipments are served by that instance of the UDM.

For more information on the Target NF Type, supi, and gpsi parameters, see
the Parameter List table in AMF Provide Positioning Info Query on page 13.

For more information on the cache feature, see Destination Selection on page

The Nnrf_NFManagement service is used for registering the 5G GMLC NF Profile
to the NRF server to inform other participants of the network about the
notification callback path of the 5G GMLC.

The supported Nnrf_NFManagement services are the following:

— Nnrf_NFRegister

— Nnrf_NFUpdate(NF heartbeat)

— Nnrf_NFDeregister

Nnrf_NFRegister

This service is used for registering the 5G GMLC NF profile to an NRF server.

The 5G GMLC sends its NF profile to the NRF server, which then registers and
distributes it for the upcoming requests. In case of an unsuccessful registration
process, the 5G GMLC retries the process until any of the following occurs:

— The attempts reach the maximum limit.

— The 5G GMLC gets a permanent error response from the NRF server.

— The 5G GMLC gets a timeout.

If more NRF servers are configured and the registration process to an NRF server
fails, the 5G GMLC tries to register its NF profile to another available NRF server.

10

If the primary server becomes available after unreachability, the 5G GMLC tries
to shift back to the primary NRF server from another: the 5G GMLC tries to
register to the primary server, and if it is successful, then sends a delete request to
the previous NRF.

If the registration process is successful, the NRF sends back a HTTP2 201
Created response to the 5G GMLC.

In case of error, the NRF sends HTTP2 error messages (3xx, 4xx, 5xx).

In case the registration to all NRF servers fails, a new alarm is raised. For more
information, see Alarm Descriptions for NLG.

Nnrf_NFUpdate (NF heartbeat)

The Heartbeat messages inform the NRF server that the 5G GMLC is still alive,
functioning, and accepting communication. Heartbeat messages are periodically
sent by the 5G GMLC toward the NRF. The NRF acknowledges them by sending
back a HTTP2 200 OK message with the NFProfile, or a HTTP2 204 No
Content message. The NRF can override the default notification period during
the registration process and the 5G GMLC follows that request. If there is no
response for three consecutive times, or if an error arrives form the NRF as a
response, the 5G GMLC classifies the NRF server as unreachable and tries to
register to an available NRF.

Nnrf_NFDeregister

If the Location Notification service is no longer available on the 5G GMLC, or if
the 5G GMLC is shifted to another NRF, then an NF profile deregistration request
is sent to the corresponding NRF.

When OAuth 2.0 is configured, the NFDeregister header must include a valid
access token.

— lcsClientType (mandatory): The type of the LCS client that initiated

— lcsLocation (mandatory): The type of the positioning request, for example,

on the shape type.

There are two more important elements that can be present in the response
JSON:

— ncgi (optional): Information about the NR Cell where the user equipment is

located. This can be translated into a location estimate.

— positioningDataList (optional): The list of positioning techniques used

during the positioning of the user equipment.

If ncgi and location estimate tag are missing, the 5G GMLC responds with an
error message. For more information about the response, see 3GPP TS 29.518.

— ncgi

— servingNode

For more information on the parameters and additional information about the
request, see 3GPP TS 29.518.

following:

— 204 No Content response: If the received NotifiedPosInfo is correct and

the GMLC server is able to process it.

2.2.3

5G GMLC Indirect Communication

Operations

ENL supports indirect communication Model C options 1 and 2, as follows:

Indirect communication Model C option 1:

In active indirect communication scenarios, the nodes of the 5G GMLCis using
the 3gpp-sbi-target-apiRoot header in the request. In case of erroneous
responses for existing operations, the Server or Via headers are added. The
operations are as follows:

— Amf3GppAccessRegistration (NLG > UDM): through the

Nudm_UEContextManagement service

— ProvidePositioningInfo (NLG > AMF): through the Namf_Location

service

— EventNotify (AMF > NLG): through the Namf_Location service

Indirect communication Model C option 2:

If Model C option 2 is enabled, apart from the scenarios of Model C option 1,
the GMLC includes the following headers in the requests for target NF producer

IPv4, IPv6

The 5G GMLC can communicate on both IPv4 and IPv6 with the 5G core nodes.
5G GMLC supports fallback through preferred protocol version if the node is
unavailable, and the secondary protocol address is present.

Fallback to the not preferred IP version is only supported during connection
creation time. If any of the AMF, UDM, or NRF requests failed, IP version fallback
is not supported.

If the connection cannot be established with an IP address with a preferred IP
version type, then the 5G GMLC attempts to establish the connection two more
times. After the third unsuccessful attempt, if an IP address with a not preferred
version type is present, the 5G GMLC tries to connect to that IP address three
times. If all three attempts fail, the 5G GMLC falls back to the original IP address,
and tries to connect to that IP address.

In case of NRF, the 5G GMLC tries to reconnect until the configuration is changed
(modified or the given IP address is removed), or the 5G functionality of the
component is turned off.

In case of AMF or UDM, the 5G GMLC tries to reconnect until the given
connection is deleted from the cache, or the 5G functionality of the component is
turned off.

The preference can be set by the IP Version Preference parameter. For more
information, see the Parameters for System Settings in Cluster Level (General
Configuration) table in the System Settings section in Parameter List, NLG.

2.3.7

Cache

The 5G GMLC implements a caching function for the connections towards the
serving UDM and AMF network functions that are discovered periodically by
querying the NRF over the Nnrf SBI.

The period of the cache refresh is set by the validity period returned by the NRF.

Note:

If all requests can be served by the NFs already stored in the cache, the
5G GMLC does not send any queries or requests towards the NRF until
the validity period timer expires. If the NRF is updated by either the AMF
or the UDM during the cache validity period, it is possible that the cache
content becomes obsolete, as the 5G GMLC acts as a client only towards
the NRF, and does not get notified of the changes.

Request Timeout

When 5G access is enabled (through the GUI under Networking Connections
> Mobile Core Network > AMF/UDM > Access HTTP2), an initial discovery is
requested immediately when the connection with at least one NRF is established.
If the NRF responds with the proper information, the next query time is
determined by the end of the validity period sent back in the response.

If the NRF fails to respond within the discovery time, the request is disposed.
(The discovery time is configured through the GUI under Software Management
> NLG Components > Configuration > HTTP2 > Discovery time.) The 5G GMLC
tries to send the request two more times with discovery time. If all attempts time
out, the 5G GMLC schedules a new request 60 seconds later to prevent the NLG
from flooding the NRF with requests.

Note: — After the first request timeout, the 5G GMLC clears the

corresponding Network Function cache to avoid using potentially
outdated connections.

— If any of the on-demand discovery requests (NFDiscovery triggered
by individual LCS request) succeeds between the first attempt to
query the NRF with NFDiscovery service and the request scheduled
60 seconds later, a new Network Function service, that is not yet
saved in the 5G GMLC cache, is stored.

from the cache, either wait for the ongoing requests to receive their responses,
or terminate immediately after a set timeout to ensure connection shutdown. For

Engineering Guidelines

Ericsson recommends the following engineering guidelines:

The 5G software design is based on the assumption that the product will be
integrated into the network using the mTLS as mandated by the 3GPP standard.
This ensures mutual authentication between the network elements, provides
integrity protection for messages and encrypts the data stream, which may
contain sensitive data. In this regard, there is no other control built into the ENL
in case of disabled mTLS.

Disabling mTLS is only recommended after a comprehensive risk analysis, taking
into account the possible technical and business impacts.

For TLS, Ericsson strongly recommends installing certificates issued by a trusted
certificate authority (CA) instead of using self-signed certificates. 5G GMLC
uses three separate CA files to validate nodes it communicates with from the
5G Core. One for all the NRF, one for all the UDM, and one for all the AMF
servers. For information on how to install customized certificates, see the Secure
Communication section in System Administration Guide for ENL Cloud Native,
NLG.
